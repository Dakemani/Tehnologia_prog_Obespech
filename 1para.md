## 1. Что такое разработка ПО

**Разработка программного обеспечения** — это процесс создания, поддержки и развития программных систем, который включает:

- анализ требований;
- проектирование;
- реализацию;
- тестирование;
- развёртывание;
- сопровождение;
- вывод из эксплуатации.

### 1.1. Жизненный цикл ПО (SDLC)

Основные модели жизненного цикла:

| Модель | Особенности |
|---|---|
| **Waterfall** | Последовательные этапы, фиксированные требования |
| **V-модель** | Акцент на верификации и валидации |
| **Итеративная** | Повторяющиеся циклы разработки |
| **Спиральная** | Управление рисками на каждой итерации |
| **Agile** | Гибкость, короткие итерации, обратная связь |

### 1.2. Цели разработки ПО

- **Корректность** — система делает то, что требуется.
- **Надёжность** — работает стабильно при различных условиях.
- **Сопровождаемость** — легко читать, изменять и расширять.
- **Масштабируемость** — выдерживает рост нагрузки и данных.
- **Безопасность** — защищает данные и ресурсы.
- **Экономическая эффективность** — стоимость владения минимальна.
- **Удобство использования** — понятна и удобна для пользователя.

### 1.3. Сложность ПО

Фредерик Брукс в книге «Мифический человеко-месяц» разделил сложность на:

- **Essential complexity** — внутренняя сложность самой задачи.
- **Accidental complexity** — сложность, созданная инструментами, архитектурой, процессом.

**Задача разработчика** — минимизировать accidental complexity.

### 1.4. Технический долг

**Технический долг** — это отложенные решения, которые упрощают разработку сейчас, но усложняют её в будущем.

Примеры:
- быстрые хаки;
- отсутствие тестов;
- дублирование кода;
- устаревшие зависимости;
- отсутствие документации.

Технический долг нужно осознанно брать и планомерно возвращать.

## 2. Фундаментальные принципы проектирования

### 2.1. Абстракция

**Абстракция** — выделение существенных характеристик объекта и отбрасывание несущественных деталей.

Пример:
```python
class PaymentProcessor:
    def pay(self, amount: float) -> bool:
        raise NotImplementedError

class StripeProcessor(PaymentProcessor):
    def pay(self, amount: float) -> bool:
        ...
```

Клиент работает с `PaymentProcessor`, а не со `StripeProcessor`.

### 2.2. Инкапсуляция

**Инкапсуляция** — скрытие внутреннего состояния и предоставление доступа только через публичный интерфейс.

Плюсы:
- контроль над изменениями состояния;
- уменьшение связанности;
- возможность менять реализацию без изменения клиентов.

### 2.3. Модульность

**Модульность** — разбиение системы на части с чёткими границами.

Хороший модуль:
- решает одну задачу;
- имеет понятный интерфейс;
- слабо зависит от других модулей;
- легко тестируется отдельно.

### 2.4. Слабая связанность и сильная связность

- **Low coupling** — модули мало знают друг о друге.
- **High cohesion** — элементы внутри модуля тесно связаны общей целью.

Идеал: **слабая связанность между модулями, сильная связность внутри модуля**.

### 2.5. Разделение ответственности (Separation of Concerns)

Каждый компонент отвечает за свою часть логики.

Пример:
- UI — отображение;
- Application — сценарии использования;
- Domain — бизнес-правила;
- Infrastructure — база данных, внешние API.

### 2.6. Информационная скрытность

Модуль должен скрывать свои внутренние решения. Наружу предоставляется только стабильный интерфейс.

### 2.7. Иерархия

Система может быть организована в виде уровней абстракции. Верхние уровни используют нижние, но не наоборот.

### 2.8. Повторное использование

Повторное использование бывает:
- **чёрный ящик** — использование готового компонента;
- **белый ящик** — наследование или копирование с изменениями.

Предпочтительнее повторное использование через композицию и интерфейсы.

### 2.9. Композиция вместо наследования

Наследование создаёт жёсткую связь. Композиция позволяет гибко собирать поведение из частей.

```python
class Logger:
    def log(self, message): ...

class Service:
    def __init__(self, logger: Logger):
        self.logger = logger
```

### 2.10. Полиморфизм

Способность объектов с одинаковым интерфейсом иметь разное поведение.

### 2.11. Инварианты и контракты

**Инвариант** — условие, которое всегда истинно для объекта.

**Design by Contract** (Бертран Мейер) предполагает:
- **предусловия** — что должно быть истинно до вызова;
- **постусловия** — что гарантируется после вызова;
- **инварианты** — что всегда истинно.

## 3. Принципы написания кода

### 3.1. KISS

**Keep It Simple, Stupid** — не усложняй без необходимости.

Простое решение:
- легче читать;
- легче тестировать;
- легче сопровождать.

### 3.2. DRY

**Don't Repeat Yourself** — избегай дублирования знаний.

Важно: DRY касается **знаний**, а не просто строк кода. Два одинаковых фрагмента могут быть случайным совпадением.

### 3.3. YAGNI

**You Aren't Gonna Need It** — не реализуй функциональность, которая может никогда не понадобиться.

### 3.4. Принцип наименьшего удивления

Код должен вести себя так, как ожидает читатель. Названия, структура и поведение не должны вводить в заблуждение.

### 3.5. Fail Fast

Ошибка должна проявляться как можно раньше и как можно ближе к источнику.

Пример:
```python
def withdraw(amount):
    if amount <= 0:
        raise ValueError("Amount must be positive")
```

### 3.6. Law of Demeter

**Закон Деметры** — объект должен знать как можно меньше о внутреннем устройстве других объектов.

Плохо:
```python
order.getCustomer().getAddress().getCity()
```

Лучше:
```python
order.getCustomerCity()
```

### 3.7. CQS

**Command-Query Separation**:
- **команда** изменяет состояние, но ничего не возвращает;
- **запрос** возвращает результат, но не изменяет состояние.

### 3.8. Избегай преждевременной оптимизации

Дональд Кнут: «Преждевременная оптимизация — корень всех зол».

Сначала:
1. измерь;
2. найди узкое место;
3. оптимизируй;
4. проверь результат.

### 3.9. Правило скаута

Оставляй код чуть чище, чем он был до тебя.

### 3.10. Программируй на интерфейсы, а не на реализации

Зависи от абстракций, а не от конкретных классов.

## 4. Принципы SOLID

### 4.1. Single Responsibility Principle (SRP)

**У класса должна быть одна причина для изменения.**

Плохо:
```python
class Report:
    def calculate(self): ...
    def save_to_db(self): ...
    def send_email(self): ...
```

Хорошо:
```python
class ReportCalculator: ...
class ReportRepository: ...
class ReportMailer: ...
```

### 4.2. Open/Closed Principle (OCP)

**Класс открыт для расширения, но закрыт для изменения.**

Достигается через абстракции, полиморфизм, стратегии.

### 4.3. Liskov Substitution Principle (LSP)

**Подклассы должны заменять базовый класс без нарушения работы программы.**

Если `Square` наследует `Rectangle`, но меняет поведение `setWidth`, это нарушение LSP.

### 4.4. Interface Segregation Principle (ISP)

**Клиенты не должны зависеть от методов, которые они не используют.**

Лучше много узких интерфейсов, чем один «толстый».

### 4.5. Dependency Inversion Principle (DIP)

**Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.**

Плохо:
```python
class UserService:
    def __init__(self):
        self.repo = MySQLUserRepository()
```

Хорошо:
```python
class UserService:
    def __init__(self, repo: UserRepository):
        self.repo = repo
```

## 5. GRASP и другие паттерны ответственности

**GRASP** — General Responsibility Assignment Software Patterns.

| Паттерн | Суть |
|---|---|
| **Information Expert** | Ответственность даётся тому, кто владеет информацией |
| **Creator** | Создание объекта поручается тому, кто его использует |
| **Controller** | Отдельный объект управляет системными событиями |
| **Low Coupling** | Минимизируй зависимости |
| **High Cohesion** | Максимизируй связность внутри модуля |
| **Polymorphism** | Разное поведение через общий интерфейс |
| **Pure Fabrication** | Искусственный класс для слабой связанности |
| **Indirection** | Посредник между компонентами |
| **Protected Variations** | Изолируй изменения через интерфейсы |

## 6. Архитектурные принципы

### 6.1. Слоистая архитектура

Типичные слои:
- Presentation;
- Application;
- Domain;
- Infrastructure.

Зависимости направлены вниз или внутрь.

### 6.2. Гексагональная архитектура (Ports & Adapters)

Ядро приложения не зависит от внешних технологий. Взаимодействие идёт через порты и адаптеры.

### 6.3. Чистая архитектура (Clean Architecture)

Правило зависимостей: **зависимости направлены внутрь**.

Слои:
1. Entities;
2. Use Cases;
3. Interface Adapters;
4. Frameworks & Drivers.

### 6.4. Микросервисы

Плюсы:
- независимое развёртывание;
- технологическая гибкость;
- масштабирование отдельных сервисов.

Минусы:
- сложность эксплуатации;
- распределённые транзакции;
- сетевые задержки;
- необходимость DevOps-культуры.

### 6.5. Монолит

Монолит проще на старте, но сложнее масштабировать и сопровождать при росте.

**Модульный монолит** — компромисс: единое развёртывание, но чёткие модули.

### 6.6. Event-Driven Architecture

Компоненты взаимодействуют через события. Плюсы: слабая связанность. Минусы: сложность отладки и гарантий доставки.

### 6.7. 12-factor app

Принципы для облачных приложений:
1. Codebase;
2. Dependencies;
3. Config;
4. Backing services;
5. Build, release, run;
6. Processes;
7. Port binding;
8. Concurrency;
9. Disposability;
10. Dev/prod parity;
11. Logs;
12. Admin processes.

## 7. Принципы Domain-Driven Design

### 7.1. Ubiquitous Language

Единый язык между разработчиками и экспертами предметной области.

### 7.2. Bounded Context

Каждая модель имеет границы, в которых её термины имеют конкретный смысл.

### 7.3. Сущности и value objects

- **Entity** — объект с идентичностью.
- **Value Object** — объект без идентичности, определяемый значениями.

### 7.4. Агрегаты

**Агрегат** — кластер объектов, который изменяется как единое целое. У него есть корень.

### 7.5. Репозитории

Абстракция доступа к данным, скрывающая детали хранения.

### 7.6. Доменные события

События, фиксирующие важные изменения в предметной области.

## 8. Процессные и организационные принципы

### 8.1. Agile-манифест

Ценности:
- люди и взаимодействие важнее процессов и инструментов;
- работающий продукт важнее исчерпывающей документации;
- сотрудничество с заказчиком важнее согласования условий;
- готовность к изменениям важнее следования плану.

### 8.2. Scrum

Роли:
- Product Owner;
- Scrum Master;
- Development Team.

Артефакты:
- Product Backlog;
- Sprint Backlog;
- Increment.

Церемонии:
- Sprint Planning;
- Daily Scrum;
- Sprint Review;
- Sprint Retrospective.

### 8.3. Kanban

Визуализация потока, ограничение WIP, управление очередями.

### 8.4. XP (Extreme Programming)

Практики:
- TDD;
- парное программирование;
- непрерывная интеграция;
- рефакторинг;
- простой дизайн;
- частые релизы.

### 8.5. Контроль версий

- **Git Flow** — ветки `main`, `develop`, `feature`, `release`, `hotfix`.
- **Trunk-Based Development** — короткоживущие ветки, частые слияния в основную.
- **Feature Flags** — включение/выключение функциональности без ветвления.

### 8.6. Code Review

Цели:
- найти ошибки;
- улучшить дизайн;
- распространить знания;
- обеспечить единый стиль.

### 8.7. CI/CD

- **CI** — автоматическая сборка и тестирование при каждом коммите.
- **CD** — автоматическая доставка или развёртывание.

### 8.8. DevOps и SRE

- **DevOps** — культура сотрудничества разработки и эксплуатации.
- **SRE** — инженерные практики для надёжности систем.

### 8.9. Управление требованиями

- User Stories;
- Use Cases;
- Acceptance Criteria;
- Definition of Ready / Definition of Done.

## 9. Тестирование и обеспечение качества

### 9.1. Пирамида тестирования

1. **Unit-тесты** — много, быстрые, изолированные.
2. **Интеграционные тесты** — меньше, проверяют взаимодействие.
3. **End-to-end тесты** — мало, проверяют сценарии пользователя.

### 9.2. Виды тестирования

- функциональное;
- регрессионное;
- нагрузочное;
- стресс-тестирование;
- тестирование безопасности;
- юзабилити-тестирование;
- контрактное тестирование.

### 9.3. TDD, BDD, ATDD

- **TDD** — Red → Green → Refactor.
- **BDD** — поведение на языке бизнеса (Given-When-Then).
- **ATDD** — тесты как критерии приёмки.

### 9.4. Метрики качества

- покрытие кода;
- mutation testing;
- плотность дефектов;
- время до восстановления (MTTR);
- lead time;
- частота развёртываний.

### 9.5. Статический анализ

Линтеры, форматтеры, анализаторы кода, сканеры зависимостей.

### 9.6. Рефакторинг

**Рефакторинг** — улучшение структуры без изменения поведения.

Типичные code smells:
- дублирование;
- длинный метод;
- большой класс;
- feature envy;
- примитивная одержимость;
- длинный список параметров;
- switch statements;
- временное поле.

## 10. Безопасность

### 10.1. Принципы

- **Security by Design** — безопасность закладывается с самого начала.
- **Defense in Depth** — несколько уровней защиты.
- **Least Privilege** — минимальные права.
- **Fail Safe** — при ошибке система переходит в безопасное состояние.
- **Zero Trust** — никому не доверяем по умолчанию.

### 10.2. OWASP Top 10

1. Broken Access Control;
2. Cryptographic Failures;
3. Injection;
4. Insecure Design;
5. Security Misconfiguration;
6. Vulnerable and Outdated Components;
7. Identification and Authentication Failures;
8. Software and Data Integrity Failures;
9. Security Logging and Monitoring Failures;
10. Server-Side Request Forgery (SSRF).

### 10.3. Практики

- валидация входных данных;
- параметризованные запросы;
- escaping;
- управление секретами;
- сканирование зависимостей;
- регулярные обновления;
- логирование и мониторинг.

## 11. Производительность и масштабируемость

### 11.1. Принципы

- измеряй перед оптимизацией;
- профилируй;
- кэшируй;
- используй асинхронность;
- применяй backpressure;
- проектируй идемпотентные операции.

### 11.2. Масштабирование

- **вертикальное** — увеличение ресурсов одной машины;
- **горизонтальное** — добавление машин.

### 11.3. CAP-теорема

В распределённой системе можно одновременно обеспечить только два из трёх:
- Consistency;
- Availability;
- Partition tolerance.

### 11.4. Кэширование

Стратегии:
- cache-aside;
- write-through;
- write-behind;
- read-through.

Важно: инвалидация кэша — одна из сложных задач.

## 12. Документирование

### 12.1. Что документировать

- зачем существует система;
- как запустить;
- как устроена архитектура;
- как взаимодействовать с API;
- какие решения приняты и почему.

### 12.2. Виды документации

- README;
- ADR (Architecture Decision Record);
- API-документация (OpenAPI/Swagger);
- диаграммы (C4, UML);
- комментарии в коде (почему, а не что).

### 12.3. Принципы

- документация должна быть актуальной;
- лучше меньше, но точнее;
- код — тоже документация;
- автоматизируй генерацию, где возможно.

## 13. Антипаттерны

| Антипаттерн | Описание |
|---|---|
| **Big Ball of Mud** | Хаотичная система без архитектуры |
| **Spaghetti Code** | Запутанные потоки управления |
| **God Object** | Класс, который знает и делает всё |
| **Golden Hammer** | Использование одного решения для всего |
| **Premature Optimization** | Оптимизация без измерений |
| **Copy-Paste Programming** | Дублирование кода |
| **Magic Numbers** | Числа без объяснения |
| **Hard Code** | Жёстко зашитые значения |
| **Tight Coupling** | Сильная связанность модулей |
| **Anemic Domain Model** | Модель без поведения |
| **Vendor Lock-in** | Зависимость от одного поставщика |

## 15. Заключение

Основные принципы разработки ПО помогают:

- управлять сложностью;
- повышать качество;
- снижать стоимость изменений;
- делать системы надёжнее и безопаснее;
- ускорять обратную связь;
- улучшать командную работу.

**Важно помнить:**

1. Принципы — не догма.
2. Контекст важнее правил.
3. Баланс между качеством и сроками.
4. Непрерывное обучение и рефакторинг.
5. Лучшее решение — то, которое понятно команде и поддерживается инструментами.

> Хорошее ПО — это не только работающий код, но и код, который можно безопасно менять годами.
