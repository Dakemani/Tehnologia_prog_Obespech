# Основные принципы разработки ПО

> Конспект по основам проектирования и разработки программного обеспечения.

## 1. Введение

**Разработка ПО** — это не только написание кода, но и управление сложностью, изменениями и качеством.

**Основные цели:**
- корректность;
- надёжность;
- сопровождаемость;
- масштабируемость;
- безопасность;
- экономическая эффективность.

**Главная идея:** хорошее ПО легко понимать, изменять, тестировать и расширять.

---

## 2. Базовые принципы проектирования

### 2.1. Абстракция
Выделение существенных характеристик объекта и скрытие деталей реализации.

**Пример:** работа с интерфейсом `Repository`, а не с конкретной базой данных.

### 2.2. Инкапсуляция
Скрытие внутреннего состояния и предоставление доступа только через определённый интерфейс.

**Плюсы:**
- меньше побочных эффектов;
- проще менять реализацию;
- выше безопасность.

### 2.3. Модульность
Разбиение системы на независимые модули с чёткой зоной ответственности.

**Правило:** каждый модуль должен решать одну задачу.

### 2.4. Слабая связанность и сильная связность
- **Слабая связанность (low coupling):** модули меньше зависят друг от друга.
- **Сильная связность (high cohesion):** элементы внутри модуля тесно связаны общей задачей.

**Цель:** изменения в одном модуле не должны ломать всю систему.

### 2.5. Разделение ответственности
Каждый компонент отвечает только за свою часть логики.

**Пример:** UI, бизнес-логика и доступ к данным разделены.

### 2.6. Информационная скрытность
Модуль должен скрывать свои внутренние решения. Наружу — только стабильный интерфейс.

## 3. Принципы написания кода

### KISS
**Keep It Simple, Stupid** — не усложняй без необходимости.

### DRY
**Don't Repeat Yourself** — избегай дублирования знаний и логики.

### YAGNI
**You Aren't Gonna Need It** — не реализуй функции, которые могут никогда не понадобиться.

### SOLID

| Принцип | Суть |
|---|---|
| **S** — Single Responsibility | У класса одна причина для изменения |
| **O** — Open/Closed | Открыт для расширения, закрыт для изменения |
| **L** — Liskov Substitution | Подклассы должны заменять базовый класс без поломок |
| **I** — Interface Segregation | Лучше много узких интерфейсов, чем один общий |
| **D** — Dependency Inversion | Зависимость от абстракций, а не от конкретных реализаций |

### Дополнительно
- **Composition over inheritance** — композиция часто гибче наследования.
- **Law of Demeter** — меньше знай о внутреннем устройстве других объектов.
- **Fail fast** — ошибка должна проявляться как можно раньше.
- **Separation of Concerns** — разделяй разные аспекты системы.

## 4. Процессные принципы

### 4.1. Итеративность
Разработка идёт небольшими итерациями с регулярной обратной связью.

### 4.2. Agile-подходы
Scrum, Kanban, XP помогают адаптироваться к изменениям требований.

### 4.3. Контроль версий
Использование Git и ветвления:
- `main` — стабильная версия;
- `feature/*` — новые функции;
- `hotfix/*` — срочные исправления.

### 4.4. Code Review
Проверка кода другими разработчиками:
- повышает качество;
- распространяет знания;
- снижает число ошибок.

### 4.5. Тестирование
Основные уровни:
- **unit-тесты** — проверка отдельных функций/классов;
- **интеграционные** — взаимодействие модулей;
- **end-to-end** — сценарии пользователя.

Подходы:
- **TDD** — сначала тест, потом код;
- **BDD** — поведение системы на языке бизнеса.

### 4.6. CI/CD
- **CI** — автоматическая сборка и тестирование при каждом изменении.
- **CD** — автоматическая доставка и развёртывание.

### 4.7. Документирование
Документация должна объяснять:
- зачем;
- как запустить;
- как устроено;
- как поддерживать.

### 4.8. Рефакторинг
Улучшение структуры кода без изменения внешнего поведения.

---

## 5. Нефункциональные аспекты

- **Безопасность** — защита данных, аутентификация, авторизация, валидация.
- **Производительность** — оптимизация только после измерений.
- **Масштабируемость** — способность выдерживать рост нагрузки.
- **Надёжность** — обработка ошибок, отказоустойчивость.
- **Сопровождаемость** — простота чтения и изменения кода.

## 6. Пример упрощённого применения

Плохо:
```python
def process(data):
    # 500 строк: валидация, БД, email, отчёт, логика
    ...
```

Хорошо:
```python
def validate(data): ...
def save_to_db(data): ...
def send_email(data): ...
def generate_report(data): ...

def process(data):
    validate(data)
    save_to_db(data)
    send_email(data)
    generate_report(data)
```

**Вывод:** код стал понятнее, тестируемее и сопровождаемее.

## 7. Итог

Основные принципы разработки ПО:

- управляют сложностью;
- повышают качество;
- упрощают поддержку;
- снижают стоимость изменений;
- делают систему надёжнее и безопаснее.

**Важно:** принципы — не догма. Их нужно применять осознанно, с учётом контекста, требований и ограничений проекта.
